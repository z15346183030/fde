把 LLM 与数据系统
落到客户的生产环境里。

我是赵旭，青岛大学 2027 届。在海信的大客户项目里，我学会怎么进现场、怎么把一句「这流程太慢」拆成可验收的指标；在 10+ 个自建项目里，我学会怎么让 LLM 从 demo 变成能被评测、能被回滚的系统。

专业是纺织工程，看起来离软件很远。但纺织本质是非标制造——纤维、工艺、测试标准、成本四段互相打架，这和我现在做的事是同一件事：在约束里找一个能跑通的解。

01

现场，是需求文档写不出来的地方

FIELD DIAGNOSIS / 三个非标现场
CASE 01 海信集团 · 国内营销 企业大客户
原话「报价到交付，中间十几个人在传 Excel。」
拆解跟着胶东机场、青岛地铁这类总额超千万的项目走完全流程，把链路拆成 12 个节点，标出谁在等谁、单点耗时最长的 3 个环节，最后判断只有 2 个环节适合先上 AI——其余是权限和组织问题，上模型只会把混乱放大。
落地大客户销售 AI 工作平台、AI 物流自追踪、AI 排产规划三个场景；在集团自研智能体平台上搭业务智能体，接自研插件做功能闭环。
判断：客户说「要一个 AI」，真实诉求往往是「少等三天」。这两件事之间隔着一整套流程改造。
CASE 02 省级大创 · 聚乳酸纤维 工业产线
原话「实验室数据好看，一上产线就废。」
拆解项目负责人，从立项、资源争取到项目管理走完整条工业化链：原料价格波动 → 改性工艺 → 测试标准 → 商业化成本。四段各有各的硬约束，且互相牵制——降成本就掉耐温，提耐温就超预算。
迁移这就是客户现场的样子：没有一份干净的需求文档，只有一堆互相打架的物理约束。FDE 的第一课不是写代码，是搞清楚哪些约束是真的、哪些只是没人质疑过。
判断：先找约束，再找方案。顺序反了，方案一定会被现场推翻。
CASE 03 校园分销网络 · 创始人 小 B 渠道
原话「卖得动，但不知道下个月该进多少货。」
拆解500+ 人推广社群，年流水 50 万+。做念本酸奶校园分销时把链路拆成选品 → 进销存 → 活动 → 复购，用 Excel + Python 监控销售、库存、复购三张表，单月销售额提升 40%，沉淀成可复制的 SOP。
发现瓶颈不在预测模型，在数据口径——五个院系经销商的「一箱」定义都不一样。先把口径统一，简单移动平均就够了。
判断：数据不通的时候，先修数据。急着上模型，只会得到一份更精致的错误答案。
02

一次交付，七段链路

DELIVERY PIPELINE / 从现场到回滚
01 业务诊断 diagnose 已交付
这一段解决的问题：客户描述的是「感受」，我需要拿到的是「可测量的现状」。
  • 画流程节点图：谁发起、谁审批、谁在等谁、每个节点平均耗时多少。在海信跟项目时把报价到交付拆成 12 个节点。
  • 找瓶颈而不是找痛点：痛点是人说的，瓶颈是数据里排出来的。两者经常不是同一个。
  • 定义验收指标：把「太慢了」翻译成「平均交付周期从 21 天降到 14 天，且返工率不上升」。
  • 划边界：明确哪些是 AI 能碰的，哪些是权限、组织、KPI 问题——后者上模型只会放大混乱。
坑直接接需求开工，三周后发现真正卡住的环节根本不在需求里。
02 数据接入 ingest 部分
这一段解决的问题：客户的系统是活的，我要在不惊动它的前提下把数据取出来。
  • 源系统盘点：ERP / CRM / WMS / MES / 一堆 Excel，逐个确认接口形式（API、视图、导出、只能截图）。
  • 口径对齐：同一个「订单金额」，销售、财务、物流三张表三个数。先把定义写成文档，再写代码。
  • 增量与幂等：按时间戳或变更日志拉增量，写入侧用 upsert，保证重跑不产生重复。
  • 脏数据处理：空值、重复、单位不一致、历史脏数据。这里花的时间通常超过建模。
  • 我的现状：SQL 与 Python 数据处理是熟的（分销项目里自己搭过进销存监控）；生产级 ETL、CDC、调度与血缘还在补。
坑数据没对齐就开始做检索，最后模型答得越流畅，错得越自信。
03 检索与工具层 retrieve / tools 已交付
这一段解决的问题：模型不能凭空知道客户的业务，得给它知识（检索）和手（工具）。
  • 检索侧：文档切分策略、embedding 选型、混合召回（向量 + 关键词）、重排、引用溯源。答案必须能点回原文。
  • 工具侧：每个工具定义 schema，并标注两个关键属性——是否改变系统状态、是否需要人工审批。
  • 权限在代码层强制：不能靠 prompt 里写「请不要随便退款」。退款这类 mutating 工具，没有审批就直接抛异常。
  • 我的实践：海信智能体平台上搭业务智能体、接自研插件做闭环；跨境电商项目里把「采集 → 筛选 → 内容生成 → 上架」拆成受控的四步。
坑把权限写进 system prompt。模型被绕过的成本，比多写十行 if 高得多。
04 编排 orchestrate 已交付
这一段解决的问题：客户流程本身在变，硬编码的流水线第三周就过时。
  • 先问该不该用 Agent：路径固定的用状态机，路径开放才交给模型决策。多数场景是状态机加一个模型节点，不是全自动 Agent。
  • 人工闸门：高风险动作前插人工确认，把「人在环」做成一等公民而不是补丁。
  • 上下文工程：长会话的压缩、摘要、关键信息保活。我写过 squeeze（上下文压缩 CLI，实测省 60–87% token）。
  • 失败可恢复：每一步落 checkpoint，中断后能从断点续，而不是从头再烧一遍 token。
坑用 Agent 的自由度去解决流程问题。自由度越高，越难验收。
05 评测闸门 eval gate 已交付
这一段解决的问题：这是 demo 与生产的分界线。没有闸门，上线只是掷骰子。
  • 现场修正即标注：客户业务专家每一次改判，都是最值钱的样本——任何公开 benchmark 都给不了。
  • 样本库 + 回归：人工修正自动入库，每次改动跑全量回归，防止「修好 A 弄坏 B」。
  • 双闸门：threshold（准确率下限）+ min_cases（样本量下限）。样本只有 3 条全中也不许发。
  • 多评委一致性：LLM-as-Judge 单评委有偏，用多评委 + ICC 组内相关系数检验一致性，不达标就说明评分维度没定义清楚。
  • 我的实践：Multi-Agent Code Studio 里做了五维加权评估 + ICC 一致性检验 + 质量门控，形成「评测 → 归因 → 优化」闭环；GEO Optimizer 用同样方法做 6 维内容评分。
坑用训练集当测试集。分数很漂亮，上线第一周就被客户打回。
06 可观测 observe 在做
这一段解决的问题：客户半夜打电话说「今天答得不对」，我得能查出来是哪一步坏的。
  • trace 而不是 log：一次问答拆成检索、重排、模型调用、工具执行多个 span，逐段看耗时与输出。
  • 对齐 OpenTelemetry 的 GenAI 语义约定：模型名、token 用量、延迟按标准字段埋点，直接进客户已有的 Datadog / Jaeger，而不是另起一个黑盒看板。
  • 成本与延迟看板：P50 / P95 延迟、单次成本、失败率，按场景拆开。
  • 我的现状：做过行为数据监控（高考择校助手，200+ 用户）驱动迭代，但 OTel / span 这一套还在补，是目前最想补的一块。
坑只记录「调用成功」，不记录「答得对不对」。前者是运维，后者才是产品。
07 上线与回滚 ship / rollback 下一步
这一段解决的问题：让「出问题」成为一件可承受的事，客户才敢让你上线。
  • 影子流量：新版本先旁路跑，不接管业务，只比对输出差异。
  • 灰度与开关：按客户、按场景、按比例放量，出问题一个开关切回。
  • 模型路由：简单请求走私有化小模型（零边际成本），复杂请求才升级到云端大模型。
  • 入口护栏：PII 检测放在入口而不是出口——出口拦截意味着敏感数据已经进过第三方模型，合规上说不清。
  • 我的现状：容器化、Linux、CI/CD 在学，还没在真实客户环境跑过一次完整灰度。这一块我打算用个人项目补齐。
坑没有回滚方案就上线。第一次故障就会把前面所有信任清零。

ROADMAP / 每阶段都有一个可验证产出
P0

把评测与可观测做成肌肉记忆

2026.11 — 2027.01

我已经会做评测，但缺的是把它接进真实链路：评测不是离线跑一次，是每次改动都自动跑。

  • 把 llm-as-judge 升级成带样本库、带回归、带双闸门的完整 eval harness，接进 CI。
  • 给一个真实 LLM 应用接 OpenTelemetry，按 GenAI 语义约定埋 span，在 Jaeger 里能看到检索 / 重排 / 生成三段耗时。
  • 补 RAG 基础：切分策略对比、混合召回、重排，做一份「不同策略下召回率与答案正确率」的对照实验。
验收开源一个能一键跑通的 eval + trace 模板，README 里有一张真实的对照数据表。
P1

做一个端到端系统，从脏数据开始

2027.02 — 2027.04

多数人的作品集从干净数据集开始。我要从脏数据开始——这是客户现场的真实起点。

  • 找一个公开但脏的数据源（政务开放数据 / 电商评论 / 招投标公告），自己做清洗、口径对齐、增量入库。
  • 在上面搭一个 RAG + 工具的问答系统，带引用溯源和人工审批闸门。
  • 把 P0 的 eval harness 和 trace 直接接上去，形成一个完整闭环。
验收写一份部署报告：数据质量前后对比、检索策略选型依据、闸门拦下了哪几次回归。
